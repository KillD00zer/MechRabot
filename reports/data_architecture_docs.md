### 2. [chunks.json](file:///mnt/78AA22ECAA22A71A/K_REPO/MechRabot/kgl%20V3/chunks.json) (HybridChunker Output)

**Goal:** Breaks the document text into semantically meaningful chunks with headings attached.
**Problem:** Throws away the clean table/picture hierarchy and dumps their references into a messy `doc_items` string array, requiring custom matching to recover spatial context.
**Architecture Blueprint:**

```json
[
  {
    "text": "Raw paragraph text",
    "contextualized": "Heading Text\nRaw paragraph text",
    "meta": {
      "doc_items": [
        "self_ref='#/texts/2' parent=RefItem(cref='#/body') ... prov=[ProvenanceItem(page_no=1, bbox=BoundingBox(l=35.9, t=592.2...))]"
      ]
    }
  }
]
```

## 🏗️ The Ideal JSON Target Architecture (For Qdrant Integration)

Below is the definitive JSON schema for [final_chunks.json](file:///mnt/78AA22ECAA22A71A/K_REPO/MechRabot/kgl%20V3/final_chunks.json). This architecture is designed to solve the two biggest retrieval problems in mechanical engineering RAG: **Hallucination via incorrect images** and **Context Loss in tables/steps**.

### Schema Definition

```json
{
  "chunk_id": "string (SHA-256 hash of content & page)",
  "content": "string (The heavily formatted text, including prepended section headers)",
  "meta": {
    "source_file": "string (e.g., 'm11_SM.pdf')",
    "page_no": "integer",
    "chunk_type": "string ('text' or 'table_spec')",
    "section_path": ["string", "string"],
    "linked_images": ["string (URI)"],
    "bbox": {
      "l": "float",
      "t": "float",
      "r": "float",
      "b": "float"
    },
    "previous_chunk_id": "string",
    "next_chunk_id": "string"
  }
}
```

### 🎯 Goals & Problem Solving

#### 1. The Image Problem (Hallucination)

- **The Problem:** Previously, all chunks on Page 4 were blindly linked to all images on Page 4. If a chunk was about the Water Pump, it was receiving images of the Timing Belt, causing the Vision LLM to hallucinate.
- **The Architectural Solution (`linked_images` & `bbox`):** By extracting the bounding box (`bbox`) of both the text chunk and the images from [output_V3_fullresult.json](file:///mnt/78AA22ECAA22A71A/K_REPO/MechRabot/kgl%20V3/output_V3_fullresult.json), the pipeline calculates the spatial distance. The chunk's `linked_images` array will now only contain the specific image that is physically nearest to or overlapping that text block.

#### 2. The Table Context Problem (Lost Specifications)

- **The Problem:** Spec tables were split row-by-row for precision (e.g., `[Specs] Torque: 65 Nm`), but they lost their parent headings. When retrieved, the LLM couldn't know _what_ component was being torqued.
- **The Architectural Solution (`section_path`):** We trace the table's physical or structural location in [output_V3_fullresult.json](file:///mnt/78AA22ECAA22A71A/K_REPO/MechRabot/kgl%20V3/output_V3_fullresult.json) upwards to find its parent section heading. This heading is placed in `section_path` and physically prepended to `content` (e.g., `"CYLINDER HEAD INSTALLATION [Specs] Torque: 65 Nm"`). This ensures precise keyword matching (BM25) while feeding the LLM the exact component context.

#### 3. The Fragmentation Problem (No Overlap)

- **The Problem:** Chunks are hard-cut. If Step 4 says "Tighten to above specification," the retriever might only grab Step 4, leaving the LLM completely blind to the actual number in Step 3.
- **The Architectural Solution (`previous_chunk_id` / `next_chunk_id`):** We create a linked list. Instead of duplicating text (which balloons the database size and dilutes vector dense matching), we store the hashes of adjacent chunks. If the LLM needs more context to answer the user, the Haystack pipeline directly fetches the `previous_chunk_id` by its exact ID without needing another vector search.
